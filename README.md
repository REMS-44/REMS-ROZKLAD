# РЕМС-РОЗКЛАД v1.6.2 — quota-safe sync

Причина `resource-exhausted` локалізована.

## Що відбувалося

Після завантаження старого розкладу app.js локально:
- нормалізував старі записи;
- відновлював teacherId / disciplineId / нові поля;
- показував їх правильно.

А cloud.js порівнював цей нормалізований стан із сирими старими
документами Firestore.

У результаті одна нова зміна могла виглядати для синхронізації так,
ніби змінилися десятки або сотні старих пар.

Кожен такий запис ішов через Firestore transaction + locks.
Це й могло призвести до `resource-exhausted`.

## Що тепер

Після отримання даних із Firebase:
1. app.js нормалізує їх локально;
2. нормалізований schedule стає BASELINE для порівняння;
3. назад у Firebase старі записи автоматично НЕ переписуються.

Тому:
**змінив одну пару → синхронізується одна пара.**

## Менше записів locks

Якщо дата / пара / викладач / група / аудиторія не змінилися:
існуючі lock-документи більше не переписуються лише заради updatedAt.

Наприклад зміна примітки:
раніше могла створювати 4 додаткові lock-write,
тепер пишеться фактично сам запис заняття.

## resource-exhausted

Якщо ліміт Firebase уже був вичерпаний попередніми спробами,
він може ще певний час повертати resource-exhausted навіть на новій версії.

У такому випадку:
- дані лишаються локально;
- програма не повертає стару версію;
- немає автоматичного циклу повторних записів;
- не потрібно багато разів натискати «Зберегти».
